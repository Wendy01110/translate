## 问题与实际改动

- 单张来源已有 20 MiB 上限，但 `--pages` 原先会一次读入全部文件，高级 OCR 再为全部图片构造 base64 请求；直接端口、用例与路由也缺少共同的页数和原始字节预算。
- `core/limits.py` 新增最多 10 页与整批 20 MiB 常量，`core/ocr_input.py` 用一个纯函数复用空图、单张与累计字节检查。每张继续最多 20 MiB，等号边界可接受；重复图片按每次出现计数。
- CLI 先拒绝 11 页，再逐张读取和检查累计预算，首次超限不再读取后续路径，返回退出码 2。路由所有模式、两个 tier 组合和四层直接适配在识别、初始化、编码或请求前拒绝全局超限，不继续尝试其它层。
- OCR 翻译用例在端口调用前检查，失败结果不携带图片或文字；实时 OCR 实际处理超大新画面时清空本轮文字及补试记忆并显示失败，有效后续画面仍可恢复处理。
- 新增 `ocr_too_many_pages` 与 `ocr_batch_too_large`，沿用 `image_too_large` / `empty_image`；共用工作区格式器显示明确的页数/大小提示。保持 HTTP 适配未配置时的原错误优先级，以及预算内 OCR.space 单张 1 MB、多页拒绝和原四层分流语义。
- 同步 CLI 帮助、OCR 端口说明、README、架构/配置/OCR 设计、`.env.example` 固定预算注释、文档入口和计划索引；不新增参数、环境变量、配置回读字段、结果状态、依赖或自动拆批调用。

## 复核与剩余边界

针对性复核确认全局输入预算位于 core，共享实现仅计算长度，不解码、复制图片或调用系统/网络；先检查页数，再有界检查各页和累计字节。CLI 最多还会持有正在检查的一张新图，因此原始输入预算不等于临时分配或进程内存上限；base64、原生解码和实际提供方容量也不由本次离线验证证明。

预算内的合法输入继续使用原模型和串行分流；全局失败不会被当作可升级到 API 的识别失败。HTTP 未配置错误优先级继续保留；没有新增自动拆批、重试或并行，真实 `.env` 没有改动。当前没有关联开放 Issue，Issue 状态不适用。

本轮未操作真实桌面、截图、剪贴板、按键、OCR/翻译、Paddle 下载/初始化或 App 重启，也未提交、推送或部署。原四层 OCR 计划的 macOS 首次 Paddle 加载提醒桌面复验仍待完成，本轮不把离线预算回归作为该验收证据。
