# macOS 屏幕实时 OCR 双屏验收

> 记录日期：2026-08-21（Asia/Shanghai）
>
> 计划：[屏幕实时 OCR 翻译](../../plan/completed/2026-08-20-live-screen-ocr.md)

## 本次边界

在当前 macOS 双屏环境重新打开菜单栏 App，用只含合成英文且每 3 秒轮换的本地页面验证 `Option+Q` 圈选、实时 OCR 翻译更新和再次按键停止。用户明确允许本次非敏感屏幕圈选、当前 PaddleOCR 与翻译源调用；没有记录截屏原图、识别全文、译文或密钥。

## 问题与修复

- 真机对比确认 `Option+W` 的系统圈选可在两块屏幕使用，而 `Option+Q` 的自定义圈选只能在一块屏幕使用。
- 当前屏幕 AppKit frame 为 `(0, 0, 1512, 982)` 与 `(1512, 126, 1920, 1080)`，并启用了“显示器具有独立空间”。旧实现只创建一个 `(0, 0, 3432, 1206)` 联合 `NSPanel`；窗口 frame 保持联合尺寸，但实际交互仍受独立 Space 限制。
- 圈选器改为按 `NSScreen.screens()` 为每块屏幕创建一个透明面板，所有面板共享同一完成/取消会话和 AppKit 全局坐标。任一屏幕完成或取消时同时关闭全部面板；非当前 key window 接受首次鼠标事件并在拖拽开始时取得响应。
- 当前两屏 AppKit 与 Quartz frame 分别为 `(0, 0, 1512, 982)` / `(0, 0, 1512, 982)` 和 `(1512, 126, 1920, 1080)` / `(1512, -224, 1920, 1080)`；现有按主显示器高度翻转的固定截图坐标与该副屏布局一致，无需另改截屏算法。

## 验证结果

- 新增离线回归测试，固定“每块屏幕保留独立 frame”“为每块屏幕创建面板”“完成或取消时关闭全部面板”。
- 完整离线套件：`254 passed`。
- `git diff --check` 通过。
- 本机 AppKit 冒烟检查实际创建两个面板，尺寸分别为 `(0, 0, 1512, 982)` 与 `(1512, 126, 1920, 1080)`，随后立即关闭，未调用 OCR 或翻译。
- App 使用 macOS 正常应用终止接口退出旧实例，再从 `~/Applications/AI Translate.app` 打开当前代码。用户把合成动态测试页移到此前不可圈选的副屏，按完整步骤复验后反馈“可以了”，确认副屏圈选、动态翻译更新和再次 `Option+Q` 停止可用。
- 早先直接向已初始化 Paddle 的旧进程发送 `SIGTERM` 时，Paddle 原生信号处理器生成了 `SIGSEGV` 崩溃报告；该报告对应退出中的旧 PID，不是新版本启动失败。后续改用应用级正常终止，目标进程成功退出后再启动。

## 结论与限制

macOS 屏幕实时 OCR 已完成当前双屏布局下的真实圈选、更新和停止验收，计划移至 `completed/`。本次不证明 Windows 多屏/DPI、其它 macOS 屏幕排列、OCR.space、API 高级 OCR、普遍识别精度或系统音频转写；这些状态继续由各自计划约束。本次没有提交、推送、部署或发布。
